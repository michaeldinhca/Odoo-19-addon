# CLAUDE.md — context for AI coding assistants

Read this first. It's written so a fresh AI session can understand what
this module is, why it's built the way it is, and what to do next — without
re-deriving context from the code alone.

## What this is

An Odoo 19 Community addon (`survey_signature`) that adds a new "Signature"
question type to the Survey app. The signing widget is Odoo's own core
`web.NameAndSignature` OWL component — the exact same "Auto / Draw / Load"
signature pad used to sign a quotation or invoice on the customer portal
(`portal.SignatureForm` wraps the same component for that flow) — reused
directly, not re-implemented. That's what "copy from Odoo sign on sale
order signature" (the brief this was built from) means concretely: the UI
respondents see here is pixel-for-pixel the same widget, wired into Survey's
own answer-saving pipeline instead of `portal`'s own RPC/submit flow.

## Non-obvious things worth knowing before you touch the code

- **How the widget actually gets on the page: `<owl-component>`, not a
  custom Interaction.** Survey's own JS (file_upload, the theme module, the
  question-reveal logic) is all built on the newer `Interaction` framework
  (`@web/public/interaction`), which attaches behavior to server-rendered
  DOM — it doesn't mount OWL component trees. `NameAndSignature` **is** an
  OWL component (uses `Dropdown`, `useState`, etc.), so mounting it needs a
  different, but equally core, mechanism: register a component under
  `registry.category("public_components")`, then place
  `<owl-component name="..." t-att-props="json.dumps({...})"/>` in the
  server template (`views/survey_templates.xml`). Odoo's own
  `PublicComponentInteraction` (`web/static/src/public/
  public_component_interaction.js`, selector `owl-component[name]`) finds
  that element and mounts the registered component automatically — no setup
  code needed on this module's side beyond the registry line. This is the
  literal same mechanism `portal.views/portal_templates.xml`'s
  `portal.signature_form` template uses for the "sign this quotation" flow —
  confirmed by reading that template directly, not assumed.

- **Why no assets need to be added for `NameAndSignature` itself.**
  `web/static/src/core/**/*` (which includes `core/signature/
  name_and_signature.js/.xml/.scss`) and `web/static/src/public/**/*.js`
  (which includes `PublicComponentInteraction`) are both already part of the
  **`web.assets_frontend`** bundle. Survey's own page layout
  (`survey.layout` → inherits `web.frontend_layout` → calls
  `t-call-assets="web.assets_frontend"`) already loads that bundle on every
  survey take page, on top of survey's own `survey.survey_assets` bundle —
  confirmed by reading `web/views/webclient_templates.xml` directly. So this
  module's own `assets` entry only needs to list the files it actually
  wrote: its own component + template + scss + the `SurveyForm` patch.
  **Don't add `web/static/src/core/signature/...` to this module's manifest
  — it's already on the page.**

- **Hidden input carries a JSON string, not a bare value.** Every other
  survey answer input posts a single scalar (`<input name="{{question.id}}"
  value="...">`), read server-side as one string. A signature needs *two*
  pieces — the drawn image (`getSignatureImage()`, a `data:image/png;base64,...`
  data URL) and the typed name (`NameAndSignature` always captures a name
  alongside the drawing, same as the portal sign flow). Rather than inventing
  a second hidden input (which the generic save pipeline has no way to
  associate with the first), the JS component (`static/src/components/
  survey_signature.js`) writes `JSON.stringify({name, image})` into one
  hidden `<input class="o_survey_signature_value" name="{{question.id}}">`.
  `models/survey_user_input.py`'s `_get_line_answer_values` override
  `json.loads()`s it back apart, strips the `data:image/png;base64,` prefix
  off `image`, and stores the two pieces on two separate fields
  (`value_signature`, `value_signature_name`). If you need a third piece of
  data from the widget later, extend this same JSON envelope rather than
  adding parallel hidden inputs — there's only one value the save pipeline
  will pick up per question id.

- **`value_signature` uses `Binary(attachment=True)`, not a Many2many to
  `ir.attachment` like `survey_file_upload` does.** A signature is exactly
  one image, generated by the browser, not a file the respondent picked —
  there's no multi-file case and no original filename to preserve, so the
  M2M-of-attachments pattern `survey_file_upload` needed doesn't apply here.
  `attachment=True` means Odoo stores/manages that image as its own
  `ir.attachment` (`res_model='survey.user_input.line'`, `res_id=<this
  line>`) automatically, tied to the line's own lifecycle — core's `unlink()`
  already sweeps any attachment whose `res_model`/`res_id` match the record
  being deleted, so **no custom `unlink()` override is needed or wanted
  here**. (`survey_file_upload`'s CLAUDE.md documents the actual mistake
  this sidesteps: it originally had a redundant `unlink()` override on
  `survey.user_input` that fought with core's own cleanup and caused a
  `MissingError`. Binary+attachment fields don't have that trap because the
  attachment is scoped to the line that owns the field, not a sibling model
  the developer has to manually point cleanup at.)

- **Why there's no `controllers/` in this module, unlike
  `survey_file_upload`.** File upload needed its own AJAX endpoint because
  large files shouldn't block the page-submit request and need real-time
  progress feedback. A signature is a small PNG generated instantly in the
  browser — it rides along in the normal form POST like every other
  question's answer, through Survey's existing `type='jsonrpc'` submit
  route. `models/survey_user_input.py`'s `_save_lines`/
  `_get_line_answer_values` overrides are the only save-path code needed,
  following the exact same override pattern `survey_file_upload` uses (both
  delegate to core's `_save_line_simple_answer` — a single-value answer,
  which this is, once the JSON envelope is unpacked).

- **`SurveyForm.prototype` patch, same reason as `survey_file_upload`'s.**
  Stock Survey's `validateForm`/`prepareSubmitValues` (in `survey/static/
  src/interactions/survey_form.js`) dispatch per question type via closed
  `if`/`switch` chains — there's no extension hook for a new type to plug
  into. `static/src/interactions/survey_form_patch.js` patches both methods
  via `@web/core/utils/patch`, exactly mirroring `survey_file_upload`'s own
  patch (different only in which CSS class it looks for:
  `.o_survey_signature_value` vs `.o_survey_file_upload_value`). Multiple
  independent modules patching the same prototype methods is fine —
  `patch()` chains cleanly via `super()` regardless of install order; the
  two modules don't need to depend on each other and don't.

- **`question_container` dispatch hook, same anchor `survey_file_upload`
  uses.** Both modules inherit `survey.question_container` and insert their
  `t-if question.question_type == '<type>'` branch `position="after"` the
  same stock anchor (`//t[@t-if="question.question_type == 'matrix'"]`).
  Multiple independent view-inheritance extensions targeting the same xpath
  from different modules is normal Odoo behavior — each inherits from the
  *original* view, not from each other, so install order between this
  module and `survey_file_upload` doesn't matter.

- **`validate_question()` needed no override.** Core's `validate_question()`
  (`survey/models/survey_question.py`) only special-cases known types
  (`char_box`, `numerical_box`, `date`/`datetime`, choices, `matrix`,
  `scale`); for an unrecognized type like `signature` it falls through to
  `return {}` when the answer is truthy, and applies the generic mandatory
  check when it's falsy (`if not answer and self.question_type not in
  [...]: ... constr_mandatory ...`). Confirmed by reading the method
  directly — an empty-string posted value (what this module's JS writes
  when nothing was signed) correctly triggers the mandatory error with zero
  extra code, same as `survey_file_upload` relies on.

- **There are THREE separate per-question-type dispatch chains on the
  frontend, not just `question_container`.** The live taking flow
  (`survey.question_container`) and the backend results page
  (`survey.survey_page_statistics_question`) are two of them; the third is
  **`survey.survey_page_print`** (`survey/views/survey_templates_print.xml`)
  — the respondent-facing "Review your answers" page (reached from the
  Thank You screen's own "Review your answers" button) — a separate
  template with its own closed per-type `t-if` chain, unrelated to
  `question_container`. Missing it meant the signature saved and validated
  correctly and showed correctly during the taking flow, but the question
  title rendered with nothing underneath on the review page specifically
  (found via a real screenshot on `odoo-comm-demo`, not a guess — the exact
  same gap `survey_file_upload` had, fixed the same release). Fixed by
  `views/survey_templates_print.xml`. **If this module's question type ever
  needs another rendering surface, check all three templates, not just
  `question_container`.**

## Quick map: "I want to change X, where do I look?"

| Change | File |
|---|---|
| The question type itself | `models/survey_question.py` |
| What gets saved / how the JSON envelope is unpacked | `models/survey_user_input.py` |
| The signing widget's own behavior (wraps `NameAndSignature`) | `static/src/components/survey_signature.js` |
| The widget's markup (just a hidden input + `<NameAndSignature/>`) | `static/src/components/survey_signature.xml` |
| Where the widget is inserted into the question page | `views/survey_templates.xml` (`question_container` hook) |
| Mandatory-answer enforcement / how the value reaches the submit payload | `static/src/interactions/survey_form_patch.js` |
| Results page rendering (image + signer name per respondent) | `views/survey_templates_statistics.xml` |
| Respondent's own "Review your answers" page display | `views/survey_templates_print.xml` |
| Backend Answers tab display | `views/survey_user_views.xml` |

## Known v1 limitations

- No per-question configuration yet (e.g. forcing "Draw only", disabling the
  "Load image" tab, a custom pen color) — `NameAndSignature` supports all of
  this via props, but nothing in `survey.question` exposes it yet. Add
  fields to `models/survey_question.py` and thread them into the `props`
  dict in `views/survey_templates.xml`'s `question_signature` template if
  needed later — same pattern as `survey_file_upload`'s
  `file_upload_max_size_mb`.
- No download/export of the raw signature image as a separate file (it only
  renders inline as an `<img>` on the results page and backend form) — add
  an attachment-download link similar to `survey_file_upload`'s
  `file_upload_links` compute field if that's needed.

## When you're done with a change

Update `CHANGELOG.md` (Keep a Changelog format), bump the version in
`__manifest__.py` (Odoo format: `19.0.{major}.{minor}.{patch}`), and if you
changed one of the non-obvious decisions above, update this file.
